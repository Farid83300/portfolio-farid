# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Personal portfolio site for Farid Zaffalone (freelance PHP/React & WordPress developer, Draguignan, France). Monorepo with two independent apps:

- `frontend/` — Next.js 15 (App Router) site, deployed standalone. Also hosts the `/admin` dashboard (JWT + 2FA protected) under `app/admin/`.
- `backend/` — hand-rolled PHP 8.1+ MVC API (no framework). Consumed by the frontend for the public contact form, for the public blog/portfolio/services pages (real posts/projects/services, see below), and by the `/admin` dashboard for auth/2FA and CRUD on posts, projects, services, categories, tags, comments, contact messages, chat messages, newsletter subscribers, and image uploads.

Commit messages and UI copy are in French.

Do not scan `frontend/node_modules`, `frontend/.next`, or `backend/vendor` — they are dependency/build output and irrelevant to the code.

## Frontend (`frontend/`)

### Commands

Package manager is **yarn** (`yarn.lock` is the source of truth — do not use `npm install`/`npm run` or generate a `package-lock.json`).

```bash
yarn dev      # dev server, http://localhost:3000
yarn build    # production build
yarn start    # serve the production build
yarn lint     # eslint
yarn format   # prettier --write .
```

No test suite exists in this project.

Requires `frontend/.env.local` (see `.env.local.example`) with `NEXT_PUBLIC_API_URL` pointing at the backend. The user runs the backend via **MAMP** (Apache on `:8888`, `backend/` symlinked into MAMP's `htdocs` as `portfolio-farid-backend`), so the working value is `http://localhost:8888/portfolio-farid-backend/public` — the PHP built-in server (`http://localhost:8000`) also works as a fallback (`php -S localhost:8000 -t public` from `backend/`) but isn't what's normally running locally. Only one of these should be up at a time; if the Next dev server can't reach the API, check `lsof -i :8888`/`:8000` before assuming the code is broken.

- Each page composes section components from `components/common/` (many numbered variants like `Services`, `Services2`, `Services3` — these are legitimate alternate section layouts mixed into the single surviving demo, not per-demo duplicates; don't assume unused ones are dead).
- `components/homes/home-1/` holds the hero/testimonials pieces specific to the one surviving home page.
- `components/common/CommonComponents.jsx` is mounted on every page and renders global floating UI: `Chat`, `ScrollTop`, `Sidebar`, `MobileMenu`.
- Styling is SCSS under `public/assets/scss/`, imported once in `app/layout.js` via `main.scss`. Bootstrap 5 + custom template SCSS. All SCSS/CSS lives under `public/assets/scss/` (or `public/assets/css/`) — including scoped CSS Modules like the admin dashboard's, never colocated next to the `.jsx` files that use them.
- **Blog, portfolio and services content is real, API-backed data** — `/blog`, `/blog-details/[slug]`, `/blog/category/[category]`, `/blog/tag/[tag]`, `/project`, `/project-details/[slug]`, `/service`, and `/service-details/[slug]` all fetch from the backend via `lib/publicApi.js` (`getPosts`, `getPost`, `getProjects`, `getProject`, `getServices`, `getService`) instead of static local data. `publicFetch()`'s underlying `fetch` uses `next: { revalidate: 3600 }` (changed from `cache: 'no-store'` on 2026-09-12, see Performance section — ISR, not a fresh backend hit on every visit). `uploadUrl(path)` in the same file builds the full image URL from `NEXT_PUBLIC_API_URL` + the relative path the API returns (e.g. `articles/xxx.webp`) — those origins must be listed in `next.config.mjs`'s `images.remotePatterns` for `next/image` to accept them.

- **`/blog-details/[slug]` 500 in production, `isomorphic-dompurify`/jsdom removed from the server path (2026-09-11)**: every article page 500'd in production (never reproduced locally, not in `next dev`, not in `next build && next start` against either the local or the real prod API — identical code, identical data, worked every time locally). Vercel's runtime logs showed the real cause, invisible from the generic `500: Internal Server Error` page: `Error: require() of ES Module /var/task/frontend/node_modules/@exodus/bytes/encoding-lite.js ... code: 'ERR_REQUIRE_ESM'`, thrown *inside* `jsdom`'s dependency chain (`html-encoding-sniffer` → `@exodus/bytes`, the latter published as pure ESM — `"type": "module"` in its own `package.json` — required via plain CommonJS `require()`, which Node refuses outright). `isomorphic-dompurify` (the sanitizer `BlogDetails.jsx` used before this fix, see the note above in Architecture) pulls in `jsdom` to sanitize HTML server-side, since there's no native DOM in Node. Two things made this hard to pin down: (1) it was **intermittent for the same URL** — the Vercel logs showed the identical route flipping between 200 and 500 within seconds, consistent with a module-loading race on serverless cold starts rather than a deterministic crash, and (2) a first fix attempt — adding `isomorphic-dompurify`/`jsdom` to `next.config.mjs`'s `serverExternalPackages` (the official Next.js option to stop the bundler from tracing/transforming a package and defer to Node's native `require()` against real `node_modules` instead) — **did not fix it**, confirmed by redeploying and seeing the exact same `ERR_REQUIRE_ESM` in fresh logs; that option was reverted. The theory (unverified, since the crash itself was never reproducible outside Vercel's specific bundling/packaging pipeline) is that Vercel's own Node output-file-tracing for the serverless function — separate from whatever Next.js's bundler does — has the same fundamental problem regardless of whether Next bundles the package or leaves it external. The fix that actually worked: stopped using `isomorphic-dompurify`/jsdom on the server at all. `lib/sanitizeHtml.js`'s `sanitizeContentHtml()` (built on `sanitize-html`, a pure-JS HTML parser/sanitizer — `htmlparser2`-based, no DOM emulation, no jsdom, no ESM-only sub-dependencies) replaces it in `BlogDetails.jsx` only. `ProjectDetails.jsx` was **not** touched and still uses `isomorphic-dompurify` — it's a client component (`'use client'`, needed for the gallery swiper), so `DOMPurify.sanitize()` there only ever runs in the browser (native DOM, no jsdom involved), which is why its `/project-details/*` pages were confirmed 200 in the same Vercel logs the whole time this was broken — never at risk from this bug in the first place. A first, since-abandoned attempt at *this* part of the fix made `BlogDetails.jsx` itself a client component (mirroring `ProjectDetails.jsx`) — reverted before deploying, without ever testing it in prod, once it became clear Next.js still executes client components on the server to produce the initial SSR HTML (that's how hydration works), so the same jsdom code path — and likely the same crash — would probably still run either way; a content page's HTML also needs to exist in that initial server response for the site's SEO to mean anything (see the canonical/sitemap work above), ruling out `next/dynamic(..., { ssr: false })` too. `sanitizeContentHtml()` allows an `img` tag (not in `sanitize-html`'s default allowlist, needed since admin-authored article HTML can embed images) on top of the library's defaults, and widens `a`'s allowed attributes to include `rel`. Verified: sanitization still strips `<script>`, `onerror`/inline event handlers, and `javascript:` URLs exactly as before; confirmed fixed against the live production site (previously-500ing article URLs now load correctly) after redeploying.
- **Cookie consent (2026-09-05)**: `app/layout.js` used to load Google Analytics (`G-J7VRJ4H2H5`) and Microsoft Clarity (`uetk0l9p9w`) unconditionally in `<head>` — that was a RGPD/CNIL compliance gap (analytics cookies require consent). ### Admin dashboard (`app/admin/`)

Client-side React admin UI, isolated from the public site (no shared header/footer/global chrome — each `/admin/*` page composes only `AdminSidebar` via `app/admin/layout.jsx`).

- `app/admin/layout.jsx` — auth guard (redirects to `/admin/login` if no JWT in `localStorage`; redirects to `/admin/security` if the token's `scope` is `setup_2fa`, forcing 2FA setup before anything else is reachable).
- `app/admin/login/page.jsx` — email/password + conditional TOTP code field (2-step, same form).
- `app/admin/security/page.jsx` — 2FA enrollment (QR code via the `qrcode` npm package, rendered client-side from the backend's `otpauth://` URI) and disable flow.
- `app/admin/{messages,chat,newsletter,comments}/page.jsx` — list/moderate views over contact messages, chat widget messages, newsletter subscribers, blog comments.
- `app/admin/{articles,projects,services}/` — CRUD (list + `new/` + `[id]/edit/`) over posts/projects/services, using shared `components/admin/{PostForm,ProjectForm,ServiceForm}.jsx`. `PostForm` has status/publish date/category select (with inline "create category")/tag checkboxes (with inline "create tag")/featured image upload+alt/SEO fields; `ProjectForm` has subtitle/category (free text)/client/role/date/CSV tags/features (one per line)/live URL/sort order/thumbnail upload/cover image upload/preview image upload (see below)/multi-image gallery upload/SEO fields; `ServiceForm` has status (draft/published)/icon (Font Awesome class)/description/sort order/single image upload+alt/SEO fields, plus a repeatable "sections" editor (add/remove blocks of heading + one-paragraph-per-line textarea) that maps to the `sections` JSON column consumed by the public detail page.
- `lib/adminApi.js` — fetch wrapper: reads `NEXT_PUBLIC_API_URL`, attaches the `localStorage` access token, and (since the 2026-09-10 security pass) transparently retries once via `POST /admin/refresh` on a 401 before redirecting to login — see Security hardening section for why tokens live in `localStorage` rather than a cookie. Also exports `adminUploadFile(file, dir)` for image uploads — sends `multipart/form-data` (no `Content-Type` header, left to the browser for the boundary) to `POST /admin/uploads`, `dir` is one of `articles`, `projects`, `projects/gallery`, `projects/preview`, `services`; `adminDeleteFile(path)` for `DELETE /admin/uploads`; and `logout()`, which revokes the refresh token server-side (`POST /admin/logout`) before clearing local storage — used by `AdminSidebar`'s "Déconnexion" button instead of a bare local clear.
- Styling: `public/assets/scss/admin/admin.module.scss`, a CSS Module imported via the `@/public/assets/scss/admin/admin.module.scss` alias — deliberately not merged into `main.scss` so the public site's global styles are untouched.
- The floating "Message Direct" chat widget (`components/common/Chat.jsx`, 2026-09-05) is wired to the backend: `POST /chat-messages` (public, validates name/email/message) feeds the same `chat_messages` table the admin already moderates. On success it shows a `react-toastify` success toast and resets the form; on failure (validation or network) it shows an error toast and keeps the entered values. Same pattern as the newsletter signup form (also wired, see below) and the blog comment form (`components/blog/Comment.jsx`, 2026-09-06, `POST /comments`) — same toast/reset behavior, plus its submit control was fixed from an `<a href="#">` to a real `<button type="submit">` (the `href="#"` was causing the page to jump back to the top on every submit, since that's the browser's default behavior for an empty-hash anchor — same footgun family as the newsletter button below, an icon/CTA-looking element inside a `<form>` that isn't actually a submit control).
- **Project preview button/modal (2026-09-08)**: `ProjectDetails.jsx`'s "Aperçu du site" control now has two modes depending on what's set on the project. ### Performance (2026-09-12)

A PageSpeed Insights-driven pass, prod-tested throughout (`https://www.faridzaffalone.com`), continuing the 2026-09-11 optimization work above.

- **RÈGLE ABSOLUE : ne jamais toucher FontAwesome.** Explicitement demandé par l'utilisateur, à plusieurs reprises, après qu'une tentative de migration vers `@fortawesome/react-fontawesome` + les packages `free-*-svg-icons` (icônes SVG React au lieu du CSS/webfont `<i className="fa-...">`) a été rejetée pour raison visuelle (`git reset --hard` sur tout le travail) — et qu'un essai manuel de subsetting des polices (`fonttools`/`pyftsubset`, ne réduire les `.woff2` qu'aux glyphes réellement utilisés) a également été tenté et rejeté pour la même raison. Le CSS actuel est **Font Awesome Pro** (licence commerciale, héritée de l'achat du template Reeni — pas de compte/Kit Font Awesome propre à l'utilisateur), et utilise des styles exclusifs à la version Pro (`fa-sharp`, `fa-light`, sans équivalent gratuit) en plus de solid/regular/brands — c'est très probablement pourquoi la conversion vers les packages gratuits rendait mal. FontAwesome représente à lui seul ~1,65 Mo (CSS ~440 Ko + 4 fichiers `.woff2` ~1,22 Mo) et est le principal plafond du score mobile PageSpeed (~50-60/100, contre ~90+ sur desktop) — **c'est un choix assumé par l'utilisateur, pas un problème à résoudre.** Ne pas proposer de nouvelle tentative de remplacement/subsetting sans que l'utilisateur ne le redemande explicitement.
- **PurgeCSS au build de prod** (`postcss.config.js`, nouveau fichier) : `@fullhuman/postcss-purgecss`, actif uniquement quand `NODE_ENV === 'production'` (jamais en dev, où le Fast Refresh de webpack réinjecte des classes à la volée). Réduit `main.scss` compilé de ~986 Ko à ~645 Ko (-35%) en éliminant les composants Bootstrap jamais utilisés (modal/carousel/tooltip/popover/accordion/offcanvas/toast — le site n'utilise ni `bootstrap.bundle.min.js` ni aucun composant JS Bootstrap, confirmé par grep) et une bonne partie d'Animate.css (v3.4.0, seules quelques classes `fadeInUp`/`fadeInLeft`/`zoomIn` réellement utilisées via WOW.js). FontAwesome est protégé par un safelist `greedy: [/^fa/]` — vérifié octet par octet après purge : les ~4300 sélecteurs FontAwesome ressortent identiques, à une exception négligeable et assumée près (le sélecteur `:host,:root{--fa-font-*}` perd son `:host,` — pseudo-classe Shadow DOM, jamais utilisée sur ce site, PurgeCSS ne permet pas de la protéger via son API de safelist basée sur les noms de classe). Un `postcss.config.js` personnalisé désactive les plugins par défaut de Next.js (`postcss-flexbugs-fixes`, `postcss-preset-env`) — ils sont donc réinstallés en dépendances et réintégrés manuellement dans le fichier, sinon les préfixes vendeurs disparaissent silencieusement du CSS de prod.
  - **Safelist complète nécessaire pour les classes injectées dynamiquement en JS par des libs tierces** (jamais écrites littéralement dans le JSX, donc invisibles pour le scanner de contenu de PurgeCSS) : `/^fa/` (FontAwesome), `/^swiper/` (Swiper), `/^odometer/` (Odometer.js — **piège découvert en premier build** : sans ce motif, les 13 classes `.odometer-*` des compteurs animés de `Facts.jsx`/`OdometerComponent.jsx` disparaissaient entièrement, cassant leur affichage), `/^Toastify/` (react-toastify), `/^wow$/`/`/^animated$/` (WOW.js), `/^tmp-/`/`/^ft-/` (classes custom du template, certaines togglées dynamiquement). Toute nouvelle lib qui injecte ses propres classes CSS via JS (pas littéralement dans un fichier scanné par `content: [...]`) doit être ajoutée à ce safelist ou son rendu cassera silencieusement au build de prod uniquement (invisible en dev).
  - **`content` doit couvrir `utils/` aussi, pas seulement `app/`/`components/`/`data/` (bug réel rencontré, corrigé le jour même)** : `utils/toggleSidebar.js`/`toggleMobilemenu.js`/`toggleDemoModal.js` togglent des classes (`sidemenu-active`, `tmp_side_bar_open`...) via `document.querySelector(...).classList.add/remove(...)` — du JS pur, jamais de JSX, donc hors du scan de contenu initial (`content: ['./app/**/*.{js,jsx}', './components/**/*.{js,jsx}', './data/**/*.js']`). Conséquence concrète : `.sidemenu-active .overlay_close_side_menu {...}` (la règle qui rend l'overlay de la sidebar visible/cliquable) a été entièrement supprimée du CSS de prod — la sidebar (`Sidebar.jsx`, panneau "Rejoignez moi" ouvert depuis `Header1.jsx`) s'ouvrait toujours (son propre `tmp_side_bar_open` a survécu, protégé par le greedy `/^tmp-/` car composé avec `tmp-sidebar-area` sur le même élément) mais ne se refermait plus au clic en dehors, seule la croix fonctionnait encore. `content` inclut maintenant `./utils/**/*.js`. Le piège général : toute classe togglée par `classList.add/remove` depuis un fichier hors de `content` disparaît silencieusement du CSS de prod (jamais en dev) sans qu'aucune erreur de build ne le signale — si un futur `classList.add(...)` est ajouté dans un fichier en dehors de `app/`/`components/`/`data/`/`utils/`, soit l'ajouter à `content`, soit passer par le safelist `greedy` du motif de préfixe de la classe.
  - **Piège de cache de build Vercel** : le premier déploiement de ce changement a semblé ne rien changer en prod (CSS toujours à 986 Ko, même hash de fichier qu'avant) alors que le build local produisait bien le CSS purgé et que les logs de build Vercel ne montraient aucune erreur. Cause : Vercel réutilise le cache `.next/cache` entre déploiements, et l'ajout d'un **nouveau** fichier `postcss.config.js` n'a pas été détecté comme motif d'invalidation — le CSS n'a donc jamais été recompilé. Fix : redéployer depuis le dashboard Vercel (Deployments → "..." sur le déploiement → Redeploy → décocher "Use existing Build Cache"). Si un changement de config CSS/PostCSS/Sass semble ne jamais s'appliquer en prod malgré un build "réussi", suspecter ce piège en premier — comparer le hash du fichier CSS servi (`curl -sD - <url>/_next/static/css/*.css`) entre avant/après plutôt que de se fier au statut "Ready" du déploiement.
- **CLS 0,853 → 0 : `display: 'swap'` → `display: 'optional'`** sur les polices `next/font/google` (Rajdhani, Rubik) dans `app/layout.js`. Un rapport Lighthouse local a révélé que le remplacement de la police de secours par la vraie police (comportement de `swap`) faisait re-flow tout le `<body>` — même avec l'ajustement automatique des métriques de fallback de Next.js, un léger changement de hauteur de ligne répété sur ~10 000px de page suffit à faire exploser le score CLS (calculé sur la fraction de viewport affectée, pas juste la distance du décalage). `optional` n'affiche la vraie police que si elle est prête très vite (~100ms) ; sinon garde le fallback pour cette visite sans jamais re-dessiner après coup. Les polices étant auto-hébergées (donc précaché/preload automatique par Next.js), le risque de rester bloqué sur le fallback est faible en pratique — vérifié : CLS 0,853 → 0 en local ET en prod réelle (PageSpeed Insights), rendu visuel identique.
- **ISR sur les pages de détail via `generateStaticParams`** (`blog-details/[slug]`, `project-details/[slug]`, `service-details/[slug]`) : ces 3 routes n'avaient pas de `generateStaticParams`, donc Next.js les traitait comme entièrement dynamiques (`Cache-Control: private, no-store`, `x-vercel-cache: MISS` — rendu serveur complet à chaque visite), contrairement à l'accueil/`/about`/`/service`/`/project` qui servent une version statique en cache. Ajout de `generateStaticParams()` dans chacune (via `getPosts()`/`getProjects()`/`getServices()`, déjà existants) : ces pages deviennent statique + ISR (`revalidate: 1h`, `Cache-Control: s-maxage=3600, stale-while-revalidate`), même mécanisme que l'accueil. `dynamicParams` reste à sa valeur par défaut (`true`) : un slug publié après le déploiement est quand même rendu à la demande au premier visiteur puis mis en cache — pas besoin de rebuild pour qu'un nouvel article/projet/service apparaisse.
- **Fond décoratif du banner en WebP** : `public/assets/images/banner/banner-background-one.jpg` (44 Ko, motif de lignes diagonales chargé en CSS `background-image` sur `.tmp-banner-one-area` — accueil + tous les bandeaux breadcrumb, donc toutes les pages) converti en `.webp` (qualité 85, `cwebp`) → 24 Ko (-47%). À ne pas confondre avec `banner-user-image-one.webp` (la photo de Farid dans le Hero) — **celle-ci est explicitement hors-limites aussi** ("déjà une image IA optimisée, aller plus loin la dégrade visuellement", refus explicite de l'utilisateur) : ne proposer aucune recompression/reconversion dessus.
- **Redis désactivé sur o2switch (2026-09-12)** : le compte o2switch avait un service Redis (cPanel "Redis Manager") à l'état arrêté, jamais branché au backend (confirmé par grep — aucune référence à Redis nulle part dans `backend/`, qui n'a pas de couche de cache applicative). Désinstallé pour libérer les ressources allouées ; à réinstaller seulement si une vraie couche de cache applicative est ajoutée un jour.
- **Ce qui reste dans le rapport PageSpeed mobile et pourquoi ce n'est pas (forcément) à corriger** : "CSS inutilisé" résiduel (~100-150 Ko) — attendu, PurgeCSS scanne le contenu de *toutes* les pages combinées, Lighthouse audite l'usage sur *une* page à la fois ; du JS "ancien"/legacy (~12 Ko) et JS inutilisé (~20-30 Ko) — pas encore investigué ; le poids FontAwesome (~1,65 Mo) — voir règle absolue ci-dessus, hors sujet. Le score mobile restera probablement plafonné autour de 50-60/100 tant que FontAwesome n'est pas touché ; le desktop tourne à 88-92/100.
- **Outillage de test utilisé pendant cette passe, à réutiliser** : jamais de `rm -rf .next && yarn build`/`yarn dev`/`yarn start` dans `frontend/` directement si l'utilisateur a potentiellement un `yarn dev` en cours dessus (vérifier `lsof -i :3000` d'abord) — un build de prod écrase le cache `.next` du serveur de dev en cours et le casse. L'API PageSpeed Insights publique (`pagespeedonline.googleapis.com`) a un quota gratuit à 0 requête/jour sans clé API — inutilisable telle quelle pour des vérifications automatisées ; demander à l'utilisateur de lancer PageSpeed Insights manuellement et de coller les résultats/URL du rapport reste la méthode fiable.

## Backend (`backend/`)

### Commands

```bash
composer install
cp .env.example .env    # fill in DB + JWT_SECRET
```

No built-in dev-server script or test suite is defined (`composer.json` has no `scripts` key). `public/.htaccess` rewrites everything to `public/index.php`, which implies Apache/MAMP as the intended local server (comments in `AuthMiddleware.php` reference MAMP explicitly for the `Authorization` header workaround). To run with PHP's built-in server instead: `php -S localhost:8000 -t public`.

Since MAMP symlinks the whole `backend/` folder (not just `public/`) into htdocs, `backend/.htaccess` denies direct access to everything at that level (`.env`, `vendor/`, `database/`, `scripts/`, `composer.*`) and `public/.htaccess` re-grants access for its own subtree — this is what actually keeps DB credentials and the JWT secret from being fetchable over HTTP. If you ever add a new top-level folder under `backend/` that needs to be browser-reachable, it needs its own `Require all granted` override the same way.

**New database (fresh install, e.g. production on o2switch): run `database/schema.sql` alone.** It's a consolidated dump (generated 2026-09-06, kept current through `migrations_v8.sql`) of the cumulative result of all migration files below, including the `services` seed data — one import, no ordering to think about.

**Existing database (upgrading local dev after pulling a new migration): apply only the new numbered file(s) you don't have yet**, in order: `database/migrations.sql`, then `database/migrations_v2.sql` (adds `users.totp_secret`/`totp_enabled`, `chat_messages`, `newsletter_subscribers`), then `database/migrations_v3.sql` (adds `categories`, `tags`, `post_tags`; renames `posts.cover_image` → `featured_image` and adds `featured_image_alt`/`excerpt`/`category_id`/`status`/`views_count`/`meta_*`; adds `projects.category`/`subtitle`/`client`/`role`/`project_date`/`tags`/`features`/`thumbnail`/`cover_image`/`live_url`/`gallery`/`meta_*`/`views_count`/`sort_order` and drops the old `projects.image_url`/`link`), then `database/migrations_v4.sql` (adds `rate_limits`, used by `Services/RateLimiter.php` to throttle login/2FA brute-force and, since 2026-09-10, the public write endpoints too), then `database/migrations_v5.sql` (adds the `services` table — `title`/`slug`/`status` (`draft`/`published`)/`icon`/`description`/`sections` (JSON)/`image`/`image_alt`/`meta_*`/`sort_order`/`views_count`; also seeds it with the 6 real services that used to be hardcoded in `frontend/data/services.js`), then `database/migrations_v6.sql` (adds `newsletter_subscribers.viewed_at`, used to make the sidebar's "Newsletter" badge count only new/unseen subscribers instead of the total — see Admin dashboard section), then `database/migrations_v7.sql` (adds `projects.preview_image`, the fallback screenshot shown in a lightbox modal on the project detail page when `live_url` is empty — see Admin dashboard section), then `database/migrations_v8.sql` (adds `refresh_tokens`, used by the refresh-token rotation/revocation system — see Security hardening section) against the DB named in `.env` (`DB_NAME`). These are plain numbered SQL files applied by hand — there's no migration runner/tracking table.

**Whenever a new `migrations_vN.sql` is added, update `database/schema.sql` to match** (it does not regenerate itself) — either by hand-editing it or by re-dumping structure from a fully-migrated local DB (`mysqldump --no-data`, strip the `AUTO_INCREMENT=N` values, keep the `services` seed `INSERT` at the end) and re-verifying it imports cleanly into an empty database. **This has only ever been run against local dev** — there is no production database yet, so when one is stood up, run `schema.sql` against it before deploying the corresponding backend code.

### Architecture

Minimal hand-rolled MVC, PSR-4 autoloaded under `App\` → `src/`:

- `public/index.php` — front controller: applies `CorsMiddleware`, boots `App`, includes `routes/api.php`, dispatches.
- `routes/api.php` requires `routes/public.routes.php` and `routes/admin.routes.php`, both given the `$router` instance.
- `src/Core/Router.php` — exact-match routing plus `{param}` placeholders (converted to regex capture groups on dispatch, params passed as extra args to the handler after `$request`); exact matches are tried first so pre-existing param-less routes are unaffected.
- `src/Core/{Request,Response}.php` — thin wrappers (JSON body parsing, JSON responses).
- `src/config/Database.php` — PDO singleton (mysql, reads `src/config/config.php`, which reads `.env`).
- Auth: `AuthService` (bcrypt hashing + `firebase/php-jwt` signing/verification, JWTs carry a `scope` claim: `full` or `setup_2fa`, 30 min expiry) + `TotpService` (wraps `spomky-labs/otphp` for TOTP secret generation/verification) + `AuthMiddleware::handle(string $requiredScope = 'full')` (expects `Authorization: Bearer <token>`, reads it via `getallheaders()` with `$_SERVER` fallbacks for FastCGI/MAMP; `'full'` tokens satisfy any required scope, `'setup_2fa'` tokens only satisfy routes explicitly requiring that scope or `'any'`) + `Models/RefreshToken.php` (opaque, DB-backed, rotating refresh tokens — see Security hardening section below for the full picture).
- 2FA is **mandatory**: a successful password login for a user with `totp_enabled = 0` returns a `setup_2fa`-scoped token (only good for `/admin/2fa/*`), not a usable session — the frontend forces enrollment before anything else is reachable. A user with 2FA enabled must submit `{email, password, code}` together to get a `full` token.
- Controllers split `Controllers/Admin/*` (JWT-protected, behind `AuthMiddleware::handle()`) vs `Controllers/Public/*` (open, for the frontend to consume).
- Image uploads: `Services/UploadService.php` validates (jpg/jpeg/png/webp/gif, extension **and** real MIME type via `mime_content_type()`/`getimagesize()` — a renamed non-image file is rejected even if its extension is on the allow-list) and moves an uploaded file into `public/uploads/{articles|projects|projects/gallery|projects/preview|services}/` with a slugified+uniqid filename, returning the relative path stored in DB. Size cap is ≤4 MB for every dir except `projects/preview` (the "site pas en ligne" modal screenshot, see Admin dashboard section), capped at 10 MB instead (`DIR_MAX_SIZE_BYTES` in `UploadService.php`) since those are often full-page/high-res captures — **MAMP's PHP `post_max_size` must be ≥ that 10 MB** (bumped via MAMP's Preferences → PHP tab, not by hand-editing `php.ini`, so MAMP doesn't silently revert it) or a large preview upload fails with an empty `$_FILES` instead of a clean error, since PHP drops oversized multipart bodies before user code ever runs. `Controllers/Admin/UploadController.php` (`POST /admin/uploads`) reads `$_FILES`/`$_POST` directly — the only endpoint that bypasses `Core/Request`'s JSON body parsing, since it's multipart. `DELETE /admin/uploads` (same controller's `destroy`, added 2026-09-08) takes a normal JSON body `{path}` and calls `UploadService::delete()` — see Admin dashboard section for why this exists and how the path is validated. Uploaded files are served as plain static files by Apache/PHP's built-in server (they exist on disk, so `public/.htaccess`'s rewrite condition `!-f` skips them) — no controller serves them. `public/uploads/.htaccess` disables script execution in that directory as defense in depth.
- `config('app.url')` (`APP_URL` in `.env`) is the backend's own browser-reachable base URL, used only to build absolute upload URLs in `UploadController`'s response (`{path, url}`). Must match whichever local server is actually running (MAMP vs PHP built-in server — see the frontend commands section above).

### Security hardening (2026-09-10)

A full pre-deployment security pass (backend headed to o2switch, frontend to Vercel). Every measure below is marked with a `SÉCURITÉ:` comment at its point of implementation in the code — grep for that to find them all.

- **Auth/JWT**: access tokens shortened from 1h to 30 min (`JWT_EXPIRE`); `AuthService`'s constructor now refuses to boot if `JWT_SECRET` is missing, under 32 chars, or still the `.env.example` placeholder — a fail-closed guard against deploying with a weak/default secret. `AuthService::verifyToken()` already checked both the HMAC signature and the `exp` claim (via `firebase/php-jwt`'s `JWT::decode`); a comment now documents that explicitly since it's easy to assume otherwise.
- **Refresh tokens + real logout** (`Models/RefreshToken.php`, `refresh_tokens` table, `migrations_v8.sql`): opaque 256-bit random tokens (not JWTs — never client-verifiable, only comparable by SHA-256 hash against the DB), issued alongside the access token on full login and on 2FA enrollment completion (`AuthController::login`, `SecurityController::enable`). `POST /admin/refresh` exchanges a valid refresh token for a new access token **and rotates the refresh token itself** (old one revoked, new one issued) — the old token stops working the instant a new one is issued. `POST /admin/logout` revokes *all* refresh tokens for the user (single-admin site, so "log out everywhere" is always the right behavior, and doubles as a compromise kill-switch). An already-issued access token still lives out its own 30 min regardless — that's the inherent tradeoff of a stateless JWT, mitigated by keeping that window short.
- **Password change** (`SecurityController::changePassword`, `PUT /admin/change-password`): didn't exist before this pass — there was no way to rotate the admin password without touching the DB by hand. Requires current password + 2FA code (same pattern as `disable()`), 12-char minimum, and revokes every refresh token on success (forces re-login everywhere, standard credential-rotation hygiene). Frontend form lives in `app/admin/security/page.jsx` below the 2FA card.
- **2FA re-enrollment now requires the password** (`SecurityController::enable`, since the previous hardening pass): a stolen/leaked access token alone can no longer be used to re-roll the TOTP secret onto an attacker's device.
- **CORS whitelist** (`CorsMiddleware.php`): `CORS_ORIGIN` in `.env` is now a comma-separated list matched against the request's actual `Origin` header (`Access-Control-Allow-Origin` is only echoed back when it matches — never a blind reflection, never `*`). Lets prod list the real domain(s) — custom domain + `www` + Vercel preview URLs if needed — without loosening the check. `header_remove('X-Powered-By')` added too (PHP version shouldn't leak via headers; `expose_php = Off` in `php.ini` is the other half, see below).
- **Rate limiting extended to public forms**: `RateLimiter` was login/2FA-only before; it's now also applied (8-10 requests / 10 min per IP) to `/contact`, `/newsletter`, `/chat-messages`, `/comments` against spam/flood, alongside explicit server-side length caps on every field (never trust the React-side validation alone). `RateLimiter::hit()` itself was fixed to use a proper sliding window (resets the counter if the last hit predates the window) — the original version, only ever used for login failures cleared by a subsequent success, would have permanently locked out any legitimate repeat visitor to these new public endpoints after their first-ever rate-limit hit.
- **Error handling / `APP_ENV`** (`public/index.php`, `config('app.env')`): in any environment where `APP_ENV` isn't explicitly `development` (so: unset counts as production — fail-safe default), PHP errors are hidden from the response and logged to `backend/storage/logs/php-error.log` instead (outside `public/`, already blocked by `backend/.htaccess`). Local `.env` sets `APP_ENV=development` for normal debugging.
- **Upload validation hardening** (already in place from the previous pass, `UploadService.php`): real MIME-type + `getimagesize()` check, not just the file extension; `public/uploads/.htaccess` disables script execution in that directory; `delete()` validates the path against the allow-list and re-resolves it with `realpath()` to stay inside `public/uploads/`.
- **HTTPS enforced** (`backend/public/.htaccess`): redirects HTTP → HTTPS, skipped for `localhost`/`127.0.0.1` so MAMP (HTTP-only) keeps working — takes effect automatically once o2switch's certificate is live on the real domain. Vercel forces HTTPS on the frontend by default, no config needed there.
- **Frontend token storage** (`lib/adminApi.js`): access token (30 min) + refresh token still live in `localStorage`, not an httpOnly cookie — documented tradeoff, not an oversight: backend (o2switch) and frontend (Vercel) are different domains, and a reliably-configured cross-site httpOnly cookie (`SameSite=None; Secure` on both ends) is more fragile to get right than a short-lived token + server-side-revocable rotation. `adminFetch`/`adminUploadFile` transparently retry once through `POST /admin/refresh` on a 401 before forcing a re-login — concurrent 401s share one in-flight refresh call (`refreshPromise`) so they can't race each other into invalidating one another's rotated token.
- **Stored-XSS mitigation** (already in place from the previous pass): `BlogDetails.jsx`/`ProjectDetails.jsx` sanitize admin-authored HTML before `dangerouslySetInnerHTML` — `ProjectDetails.jsx` (client component) still with `isomorphic-dompurify`, `BlogDetails.jsx` (server component) with `sanitize-html` since 2026-09-11 (see the `/blog-details/[slug]` 500 note in the Frontend Architecture section — swapped off `isomorphic-dompurify`/jsdom there for an unrelated production-breaking reason, sanitization coverage is equivalent either way).
- **Content-Security-Policy** (`next.config.mjs`): **production builds only** — `next dev`'s webpack Fast Refresh needs `eval()`, which a CSP without `'unsafe-eval'` blocks outright (verified: adding it unconditionally 500'd every route in `yarn dev`). Rather than weaken the prod policy for a dev-only need, the CSP header is only sent when `NODE_ENV === 'production'` (verified clean via `yarn build && yarn start`— no console/network errors across `/`, `/contact`, `/blog-details/*`, `/admin/login`). Allowlists exactly the third-party origins the code actually calls: Google Analytics + Microsoft Clarity script origins (`CookieConsent.jsx`), Google Fonts, and the backend API origin (derived from `NEXT_PUBLIC_API_URL` at build time — if that env var is wrong at Vercel build time, `connect-src` will be wrong too and every fetch will break, so double-check it on deploy). `connect-src` still also lists `https://api.emailjs.com` from when `Contact2.jsx` used to post to EmailJS — since the 2026-09-11 migration to the backend (see the "Contact forms fixed" note above), nothing actually calls it anymore; left in place as an inert unused allowlist entry rather than churn the CSP for its own sake. `'unsafe-inline'` stays for script/style since gtag/clarity inject inline scripts and the CSS pipeline (Next/Sass/Bootstrap) has no nonce plumbing — the real protection here is that arbitrary *third-party* origins are still blocked, which is what actually matters for XSS exfiltration.
- **Dependency vulnerabilities** (`yarn audit` / `composer audit`): `composer audit` was already clean. `yarn audit` found 41 vulnerabilities including **multiple critical unauthenticated RCEs in Next.js** (15.3.0 — image optimization API, React flight protocol, Windows-hosted RCE) and a critical prototype-pollution in `swiper` (11.2.10). Upgraded `next` → `15.5.25` (latest patched 15.x — deliberately stayed on the 15.x line rather than jumping to 16 to minimize breaking-change risk) and `swiper` → `12.2.0`, plus forced `postcss`/`js-yaml` (transitive, build-tooling only) to patched versions via `resolutions` in `package.json`. `yarn audit` is now 0 vulnerabilities. Verified with a full `yarn build` and manual testing of both Swiper usages (`Testimonials.jsx`, `ProjectDetails.jsx`'s gallery) — both still initialize and navigate correctly.
- **Manually verified** (not just code review): SQL injection payloads against `/posts/{slug}` and `/posts?category=` (parameterized queries hold — no error, no data leak), a stored-XSS payload through `/contact` (saved as inert text, never rendered as HTML anywhere), every protected `/admin/*` route rejecting requests with no/invalid token, and the full login → refresh → rotation → logout → revocation chain end-to-end against the real local DB (via a disposable test user, deleted afterward — the real admin account was never touched).

**Still advisory / needs action outside this codebase at deploy time** (can't be fixed by code alone): enable Cloudflare's WAF + rate limiting (and "Under Attack" mode if a spike hits) once the domain is proxied through it; set real file permissions on o2switch (644 files / 755 dirs — whatever FTP/SSH client is used to upload probably won't preserve them); disable unused dangerous PHP functions (`exec`, `shell_exec`, `system`, `passthru` — the codebase doesn't call any of them, but disabling them in o2switch's MultiPHP INI Editor is still good defense in depth) and set `expose_php = Off`; set up automatic DB backups on o2switch **and actually test a restore**, not just confirm a backup file exists; keep `CORS_ORIGIN` and `NEXT_PUBLIC_API_URL` updated to the real prod domains on both sides once they're known.
